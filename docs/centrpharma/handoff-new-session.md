# Передача контекста: лендинги ЦентрФармы → новый чат

## Почему новый чат

Lovable создал репозитории в организации **`autolandings`**
(`github.com/autolandings/page_39`, аналогично для page_40).
Текущий чат привязан к репозиториям владельца `aiaccess11gempro5693-alt`
(`n8n`, `wildberries-boost`), а среда не разрешает подключать в одну сессию
репозитории разных владельцев:

> cross-tier adds are not supported in v1: requested "autolandings/page_39"
> but session already has repos from owner(s) [aiaccess11gempro5693-alt]

Значит, работа над лендингами ведётся в отдельном чате, стартующем сразу
с репозитория `autolandings/page_39` как исходного источника.

## Что перенести в новый чат

1. Оба файла ТЗ: `page_39.docx` и `page_40.docx` (приложить в новый чат).
2. Текст ниже — целиком, одним сообщением.

## Текст для нового чата

Работаем над двумя лендингами компании ЦентрФарма. Черновики лежат в Lovable,
каждый в своём проекте, оба подключены к GitHub:
`autolandings/page_39` и `autolandings/page_40`.

К каждому лендингу есть ТЗ в .docx (приложены). ТЗ писали **разные люди**,
описывают они одно и то же предложение. Задача: довести оба черновика до
соответствия своим ТЗ. Дедлайн — пятница. Потом заказчик выберет лучший из
двух.

### Правила работы (согласованы, не отменять без явного указания)

1. **Две страницы — два независимых ТЗ.** Обе делаются целиком, каждая строго
   по своему ТЗ. Не сближать страницы между собой, не переносить содержимое
   из одного ТЗ в другое, не вычищать повторы между страницами — их будут
   сравнивать, разница авторских подходов должна сохраниться. Повторы
   вычищаются только внутри одной страницы и только если повтор есть в самом ТЗ.
2. **Источник правды — ТЗ.** Расходится страница с ТЗ — правим страницу.
   Нужно отступить от ТЗ (например, ради мобильной вёрстки) — сначала записать
   отступление в STATUS.md, потом делать.
3. **Вопросов клиенту не задаём.** Работаем с тем, что есть. Но и данных за
   него не сочиняем: «рост на Х%» в кейсах page_39 (экран 8), «ДОПОЛНИТЬ:
   количество клиентов / проектов / коммуникаций» (page_40, слайд 7),
   логотипы клиентов (page_40, слайд 17) — остаются видимыми плейсхолдерами
   в вёрстке. Все плейсхолдеры собираются одним списком в STATUS.md.
4. **Сверх ТЗ добавляем только юридический слой** — чекбокс согласия на
   обработку персональных данных у формы и ссылку на политику
   конфиденциальности в футере (адрес — плейсхолдер). Больше ничего:
   ни блоков, ни экранов, ни офферов, которых в ТЗ нет. Идеи по улучшению —
   в STATUS.md, раздел «Предложения», без внесения в вёрстку.
   Исключение: page_40, слайд 12 — там в самом ТЗ отсутствует блок «Оффер»,
   который есть у двух соседних сегментов; верстается пустой блок-заглушка
   той же формы.
5. **Служебная разметка ТЗ — не текст страницы.** Слова ЗАГОЛОВОК,
   ОСНОВНОЙ ТЕКСТ, ВЫВОД, ОФФЕР, МОДЕЛЬ, ПАРАМЕТРЫ, СХЕМА, ЦИФРЫ,
   КАРТОЧКА 1, РЕШАЕМ ЗАДАЧИ — пометки для верстальщика. Проверять первым
   делом в каждом черновике.
6. **Делаем по очереди:** сначала page_39 целиком, потом page_40. Не смешивать
   правки двух страниц в одном коммите. Порядок внутри страницы:
   сверка с ТЗ → правки контента → вёрстка и мобильная версия → юридический слой.
7. **Статус ведётся в репозитории.** В каждом репозитории лежат RULES.md
   (эти правила) и STATUS.md (чек-лист по всем экранам/слайдам, чек-лист
   правок Анны, список плейсхолдеров). Обновляются при закрытии каждого
   экрана. Не записанное в файл считается несделанным.
